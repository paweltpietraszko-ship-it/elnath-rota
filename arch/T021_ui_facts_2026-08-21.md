## 2. Realny inwentarz możliwości Elnath Rota (z kodu, nie z pamięci)

## 3. Twoja koncepcja: workspace + pokoje — zestawienie z faktami

Powiedziałeś: koordynator ma workspace z ~20 kilkoma obiektami jako
przedpokój, każdy obiekt to osobny pokój. To się **dokładnie** pokrywa z
istniejącą strukturą danych:
- workspace = `active_sites_for_coordinator()` (lista obiektów);
- wejście do pokoju = `bootstrap_or_resume_coordinator_context()` +
  `open_month()` dla wybranego Site+miesiąc;
- każdy pokój wewnątrz ma te same podsekcje (2.3–2.9 wyżej), bo backend nie
  rozróżnia obiektów strukturalnie — każdy Site ma swój profil, roster,
  grafik, decyzje, historię, analitykę osobno.

To pasuje też do struktury Continuity AI: tam "workspace" to teczka/projekt
do zbadania, tu "workspace" to obiekt (Site) do zaplanowania — ta sama
architektura nawigacji (lista → wejście → wnętrze z podsekcjami) przenosi
się koncepcyjnie, nawet jeśli same komponenty trzeba przepisać.

### 9.3 Ręczna korekta — function list

Source: `rota/application/manual_edit.py` (module docstring: covers
add/edit/cancel PRIMARY, split coverage, coverage gap repair, add/edit/
cancel TRAINEE, freeze/unfreeze — one mechanism, not one class per
button). Three public entry points, all site+month+coordinator+
effective_from scoped, all operating against the site's CURRENT
`ScheduleVersion`:

1. **`apply_manual_correction`** — generic: caller supplies a list of
   corrected/added `Assignment` objects (`upsert_assignments`), matched
   by `assignment_id` against the current snapshot (new id = add,
   existing id = edit). One `Assignment` = employee_id, start/end
   datetime, role (`PRIMARY`/`TRAINEE`), state (`PLANNED`/`REALIZED`/
   `CANCELLED`), `frozen` flag, `covers_demand_id` (which ShiftDemand
   this fulfills — shared `covers_demand_id` across two Assignments is
   how split coverage / mentor+trainee pairing is expressed),
   `mentor_primary_assignment_id` (required for TRAINEE role, absent for
   PRIMARY), optional free-text `note`.
   - **A coordinator-created HARD rule violation never blocks the
     save** — it's captured as a Deviation instead (shown after the
     fact, not a blocking modal). Important UI implication: the
     Ręczna korekta screen must show validation feedback as warnings,
     never as a hard stop.
   - If the correction creates a REST-01 (rest period) violation, the
     system auto-records a `CONFIRMED_EXCEPTION`/`INFORMATIONAL` audit
     entry (`REST_OVERRIDE_RECORD`) by itself — no separate
     coordinator justification step, but worth surfacing as "this
     creates a rest-rule exception" in the UI.
   - Never triggers an automatic REPLAN.
2. **`freeze_or_unfreeze`** — same mechanism, one field: toggles a
   single existing Assignment's `frozen` boolean by `assignment_id`.
   Frozen assignments are what "Odmroź..." (§9.1's unfreeze
   unblocking-option) reverses.
3. **`mark_not_worked`** — marks one currently `PLANNED`+`PRIMARY`
   Assignment as not actually worked: becomes `state=CANCELLED`,
   `operational_code="NN"`. Only legal on a PLANNED PRIMARY (raises
   otherwise). Leaves a coverage gap behind — the coordinator must
   separately use `apply_manual_correction` to fill it, or it shows up
   as an uncovered-demand Deviation.

All three accept an optional `responds_to_decision_required_id` — when
reached via a §9.1 "Ręczna korekta mimo zapisu..." unblocking-option
link, that id must be threaded through so the correction is recorded as
answering that specific decision (visible later in Historia i audyt).
Every correction produces a brand-new child `ScheduleVersion` (never
mutates the parent in place) — fully traceable, nothing is destructive.

### 9.3.1 NEW BACKEND REQUIREMENT (2026-08-22): dry-run check before save

Surfaced via a concrete scenario Paweł posed (swap two employees' shifts
to fix a fairness pattern — e.g. one person had two dniówki in a row,
another two nocki, coordinator wants to give each one D + one N — and
this swap happens to break a HARD rule, e.g. REST-01). Traced today's
actual behavior: `apply_manual_correction` validates AND persists in one
atomic call (confirmed — grepped `rota/application/` for
`preview`/`dry_run`/a standalone `validate` entry point: NONE exists).
There is no today mechanism to show the coordinator what deviations a
correction WOULD create before it's committed — only after, via the
returned `ScheduleVersion`'s deviations.

Paweł's decision: this is foundational, not optional — build it. New
flow: **zmiana → pytanie (ostrzeżenie z listą odchyleń) →
zapisz/odrzuć**, replacing today's zmiana → zapisz.

**This is a genuinely NEW backend function, not existing-function
content-filling** (unlike everything else gathered under §9 so far) —
flagging per CLAUDE.md discipline, not implementing here. Shape, derived
from the existing code path (not yet built, not yet reviewed by
Paweł/architect):
- A new `preview_manual_correction`-shaped application function sharing
  `apply_manual_correction`'s steps 1-8 (`assemble_planning_state` →
  `validate` → `materialize_deviations`, plus the REST-01
  `_rest_override_pairs` check) but STOPPING before
  `lifecycle.create_schedule_version` — no persistence, just returns the
  would-be `Deviation` list (+ rest-override pairs, if any) for the UI
  to render as a warning.
  - Implies extracting shared logic out of `apply_manual_correction`'s
    body (today it's one linear function, steps 1-11) so both the
    preview and the real save call the same validation path — exact
    refactor shape is an implementation decision, not decided here.
  - `freeze_or_unfreeze` and `mark_not_worked` both route through

    correction — worth confirming during implementation, not assumed

- UI flow implication: "zapisz" only becomes available after the
