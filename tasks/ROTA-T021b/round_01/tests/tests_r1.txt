  state that employee_availability_matrix() must read back after every write
- brief.md:105: the day-only exception already requires an existing Employee
- brief.md:51-88: the D/N and weekday commands accept employee_id but define
  no corresponding existing-Employee precondition

  not define the validity of the employee_id retained in that shape

- rota/planning/site_rules.py:101-105 validates only that employee_id is a
  non-empty string; the structured JSON has no Employee referential check
- record_structured_rule_decision() likewise does not resolve Employee
- rota/application/availability_matrix.py:53-65 begins by calling
  get_employee(conn, employee_id), which raises for an unknown Employee
IMPACT:
- a conforming implementation may persist D/N or weekday state for an
  arbitrary non-empty ID, after which the mandatory read/write round trip
  cannot be performed for that ID
- different wrappers for the same per-employee matrix would enforce
  different identity boundaries, and Tor 1 cannot derive the expected
  no-write behavior for unknown IDs
CLOSURE:
- define one explicit Employee identity precondition for every create command
  and for the employee retained by update/end; at minimum it must make the
  promised unchanged read projection total for every successful write
- add an equivalence-class test covering unknown employee_id across all
  affected commands and proving zero decision/rule/action writes
- if SiteMembership presence or enabled state is also intended as a command
  precondition, state it explicitly; neither this audit nor CC should invent
  that additional product rule
