R1-1 — Generated Site IDs are exported instead of endpoint templates

TRACE:

  permits only an endpoint template;
- §5.10 requires an ID privacy canary.

OWNERSHIP:
- frontend/src/diagnostics/sanitize.ts owns endpoint sanitization before an
  event enters the buffer.

REPRO:
- diagnostics.audit-r1.spec.ts, "a SITE identifier is removed...";
- create a real Site, open it, and inspect the recorded request;
- observed endpoint_template:
  /workspace/sites/SITE-3292e7cbaa664000a934684a99ff4bde/roster
- the generated SITE-* value remains verbatim because ID_SEGMENT recognizes
  hex/UUID-like values, R-* and long numeric values, but not SITE-*.

REQUIRED CORRECTION:
- normalize every actual identifier format used in decision-relevant frontend
  routes before recording/export; extend the privacy canary to the generated
  technical Site ID (and the other actual route-ID families), not only names
  typed into forms.

R1-2 — Action resolution is not causal

TRACE:
- brief.md §3.2 says the effect of the click resolves that click; a registered
  error is an allowed resolution, while no request/navigation/UI effect/error/
  explicit no-op produces ACTION_STALLED.

OWNERSHIP:
- frontend/src/diagnostics/tracking.ts owns click/effect correlation;
- frontend/src/diagnostics/globalHandlers.ts owns global-error recording.

REPRO A — registered error is also reported as a stall:
- click the unhandled-error trigger and wait past 800 ms;
- observed UNHANDLED_ERROR and ACTION_STALLED for the originating click, because
  the global error handler records the error but never resolves its action.

REPRO B — unrelated mutation hides a dead click:
- click the inert control, then mutate an unrelated body attribute within the
  800 ms window;
- ACTION_STALLED is absent because the document-wide MutationObserver treats
  any DOM mutation as the effect of that click.

REQUIRED CORRECTION:
- use one causal action-resolution invariant across request, navigation, UI
  effect, error and explicit no-op paths. An unrelated mutation must not resolve
  the click; the error caused by the click must resolve it. Keep both sibling
  cases as regression tests.

R1-3 — Malformed successful JSON is recorded as REQUEST_SUCCEEDED

TRACE:
- brief.md §1 requires the report to say whether an error occurred;
- §3.1 requires REQUEST_FAILED with an error category;
- the delivered event schema explicitly includes the "parse" category.

OWNERSHIP:
- frontend/src/api/client.ts::req owns request completion and JSON parsing.

REPRO:
- return HTTP 201 with malformed JSON from POST /workspace/sites;
- the UI shows the parsing failure, but the buffer contains
  REQUEST_SUCCEEDED and no REQUEST_FAILED(error_category="parse");
- success is recorded before res.json() completes.

REQUIRED CORRECTION:
- classify success only after the response required by the caller has been
  parsed; record a safe parse failure when parsing fails. Cover representative
  GET and mutation responses through the shared req path.
