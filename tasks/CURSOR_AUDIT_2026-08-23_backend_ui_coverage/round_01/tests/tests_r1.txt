B. INACCURACIES

B-1. The 24h checkbox is not an effective gate on every SiteProfile

Document claims:

- arch/T021_spec.md:516-528 says every roster row has a 24h column, that
  unchecked means the solver may not use the employee, and that the
  persistent can_work_24h bool remains off until toggled back on;
- tasks/ROTA-T021/brief.md:426-430 carries this toggle into Screen 2
  without an applicability exception.

Actual code:

- rota/domain.py:193-196 documents can_work_24h as a qualification only
  for a mixed 12h/24h profile and says it is ignored on an all-24h profile;
- rota/planning/eligibility.py:142-148 defines is_all_24h_profile;
- rota/planning/eligibility.py:167-173 enforces SHIFT-24-01 only when the
  profile is not all-24h;
- tests/test_t012.py:563 is the retained regression proving an all-24h
  profile ignores can_work_24h.

Therefore the persisted bool can be false while the checkbox has no effect
on eligibility at an all-24h Site. The documents describe it as an
unconditional solver permission.

B-2. ExternalSupportWindow is a datetime interval, not a date range

Document claims:

- arch/T021_spec.md:537-541 describes each support window as "date range +
  optional D/N restriction";
- arch/T021_spec.md:549-556 repeats "date range + optional D/N" for the
  per-employee list.

Actual code:

- rota/domain.py:200-208 stores start_datetime and end_datetime;
- rota/application/durable_inputs.py:112-152 writes those exact datetime
  fields;
- rota/planning/eligibility.py:195-207 requires one active window to cover
  the demand's complete [start_datetime, end_datetime] interval.

A date-only form is therefore not the actual backend shape and can change
whether an overnight D/N demand is covered.

B-3. Historia i audyt overstates material-action completeness

D. DEPENDENCY / SEQUENCING

D-1. The "existing employee" picker has no source population

Contract flow:

- tasks/ROTA-T021/brief.md:374-391 says the picker offers employees with no
  membership at the current Site and disabled LOCAL members, while excluding
  existing EXTERNAL_SUPPORT rows;
- the only read named there is list_memberships_for_site.

Actual read boundaries:

- rota/persistence/employee_repository.py:143-150
  list_memberships_for_site returns only rows that already have a membership
  at that Site;
- rota/persistence/employee_repository.py:79-84 list_employees is the
  existing all-Employee population read, but the contract never names it or
  defines a narrower coordinator-visible population.

The named read can identify disabled LOCAL and EXTERNAL_SUPPORT rows, but it
cannot discover the first required class: employees with no row at all for
this Site. The picker cannot be implemented from its stated inputs.

D-2. New Site -> empty shift catalog has no documented receiving flow

Contract link:

- tasks/ROTA-T021/brief.md:179-184 creates every SiteProfile with
  standard_shifts=[] and says the catalog will be filled incrementally in
  Panel Sterowania;
- arch/T021_spec.md:393-407 repeats that the coordinator fills the shift
  catalog there;
- coordinator_context_completeness requires at least one valid shift
  (arch/T021_spec.md:364-374), so the Site cannot become plan-ready without
  this step.

Existing backend path:

- rota/persistence/site_profile_repository.py:151-179 reads the full
  SiteProfile including standard_shifts;
- rota/application/durable_inputs.py:383-414 rewrites the full current
  SiteProfile;
- rota/planning/shift_catalog.py:95-132 owns write-time and PLAN-time
  StandardShift validation (full-hour boundaries, weekdays, rest,
  catalog-kind/duration and required-primary-count rules).

No Panel sterowania -> Obiekt section in the audited T021 documents defines
the shift rows/fields, read, complete-object update or these validation
boundaries. The producer screen intentionally creates an incomplete Site,
but its claimed consumer step is not contractually present.

D-3. In-scope Site deactivation has no UI route back to reactivation

The documents combine these facts:

- Site display_name/active editing is in scope now
  (tasks/ROTA-T021/brief.md:491-494 and owner D3);
- Workspace reads only active_sites_for_coordinator
  (tasks/ROTA-T021/brief.md:141-160);
- arch/T021_spec.md:344-381 explicitly leaves all_sites_for_coordinator out
  of the current Workspace.

Actual backend behavior:

- rota/application/durable_inputs.py:417-460 can persist Site.active=False;
- rota/application/bootstrap.py:378-386 omits inactive Sites from the
  Workspace read;
- rota/application/context.py:20-40 makes update_site itself unusable once
  that Site is inactive;
- rota/application/bootstrap.py:81-96 explicitly identifies bootstrap/resume
  as the public recovery path after this self-lock.

The current UI contract exposes neither the inactive Site nor a resume
action addressed to its existing site_id. This is a new sequencing issue,
not a repetition of the previously accepted decision that Workspace's
ordinary "Wszystkie" list means active Sites rather than an admin-wide list.

D-4. Persisted schedule handoff is incomplete

PLAN/select can create a current ScheduleVersion and Przeglad can identify
its header, but the next navigation step cannot reconstruct the schedule
grid from the documented calls. This is the vertical consequence of A-1:
the existing get_current_schedule_snapshot/get_schedule_snapshot read must
be accounted for before Planowanie miesiaca or Reczna korekta can be called
complete after reload/restart.
