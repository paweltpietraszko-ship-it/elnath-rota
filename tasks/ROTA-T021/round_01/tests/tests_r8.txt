R8-2 - THE TWO-CALL OWNER AND PARTIAL-FAILURE RETRY CONTRADICT EACH OTHER
TRACES_TO: R7-2
STATUS: FAIL
CONTRACT:
- brief.md:343-347 says the API layer sequences update_employee followed by
  update_membership and returns generated employee_id in its POST response
- brief.md:348-353 says the frontend needs that ID for the second call and
  that a failed second call is retried with the already-known ID
EVIDENCE:
- if one API POST sequences both calls, the frontend does not make the second
  call and receives a normal response only after both calls succeed
- update_employee and update_membership each own and commit a separate
  transaction (rota/application/durable_inputs.py:221-290); therefore the
  first can persist while the second fails
- in that partial-failure path the contract defines neither an error response
  that reveals the generated ID nor a retry request that accepts/reuses it;
  retrying initial creation can generate a different ID and duplicate Employee
IMPACT:
- the promised idempotent resume is not executable for the exact failure it
  is intended to cover
- CC must choose whether the API or frontend owns sequencing and must invent
  the failure/response protocol
CLOSURE:
- choose one sequencing owner and define the observable success and partial-
  failure contract, including how the original generated employee_id is
  recovered and reused without creating another Employee
- test failure injection between the two existing calls, lost/retried request,
  and successful resume with exactly one Employee and one LOCAL membership

R8-3 - GENERAL-AVAILABILITY READ STATE IS NOT DERIVABLE FROM THE RETURNED LIST
TRACES_TO: R7-3
STATUS: FAIL
CONTRACT:
- brief.md:364-375 reads all current UNAVAILABLE_24H family ends but asserts
  that at most one family is the matrix toggle's block
- brief.md:376-391 permits fresh independent families and correction/restore
  by the selected family's availability_id
- brief.md:393-410 says the absence form uses the same UNAVAILABLE_24H
  mechanism and may also create independent families
- frozen owner decision Section 5 requires automatic return to checked state
  after the inclusive end date
EVIDENCE:
- get_current_availability_for_employee returns one current row for every
  availability_id family; it supplies no provenance marking one row as
  belonging to the matrix shortcut (availability_repository.py:117-130)
- multiple UNAVAILABLE_24H families are therefore legal and indistinguishable
  by origin under the stated shared mechanism
- AvailabilityRecord.active is the current chain-end flag, not temporal
  applicability: active=True remains true after end_date has elapsed
- brief.md:371-375 renders every active=True family as unchecked without an
  evaluation date, so natural expiry would remain visually unchecked
IMPACT:
- the UI cannot deterministically choose which availability_id to correct or
  restore when zero, one or multiple blocks exist
- it also cannot satisfy the frozen automatic re-check after end_date by the
  specified active-flag rule
CLOSURE:
- define the matrix state and editable-family selection from the full list for
  zero/one/multiple UNAVAILABLE_24H families and for dates before, inside and
  after each inclusive range
- do not invent a provenance marker unless separately authorized; the current
  model has none
- test overlapping and disjoint sibling families, an inactive chain end, and
  natural expiry without a write
