  SiteMembership.enabled=True; removal sets enabled=False without deleting

  EXTERNAL_SUPPORT memberships

  brief.md:355-358 defers the support-window part required on their detail

R7-2 — NEW-EMPLOYEE PAYLOAD AND TWO-STEP CALL OWNERSHIP ARE NOT EXECUTABLE
STATUS: FAIL
CONTRACT:
- brief.md:300-307 supplies display_name, day_only, a generated employee_id
  and then calls update_employee followed by update_membership
- brief.md:80-87 forbids the API router from owning a new compound business
  operation
- T016 keeps Employee.active_from/active_to as legacy metadata: they need not
  become planning UI fields, but remain mandatory persisted constructor data
EVIDENCE:
- exact-SHA dataclass introspection gives five mandatory Employee fields:
  employee_id, display_name, active_from, active_to and day_only
- Section 5.1 maps only three of them and supplies no technical values for
  active_from/active_to
- update_employee returns None, while employee_id is generated in the API;
  the contract does not define how the frontend obtains that ID for the
  required following update_membership call
- no existing application command atomically creates Employee + membership,
  and the contract does not say which allowed layer composes the two existing
  commands or what the retry/resume behavior is after the first succeeds
- the later day_only toggle says only "toggling Employee.day_only" but does
  not require the other four current Employee fields to round-trip unchanged
IMPACT:
- implementations must invent persisted metadata, an API response and/or a
  forbidden API-owned orchestration; a day_only edit can also overwrite
  unrelated Employee data
CLOSURE:
- map every Employee constructor field without exposing retired metadata as a
  planning decision, and require day_only edits to preserve all other fields
- define the thin API response carrying the generated employee_id and assign
  the two existing calls to an allowed layer; under current T021 scope no new
  rota/** compound command may be invented
- define deterministic retry/resume after Employee exists but membership does
  not, reusing the existing-employee path rather than creating a duplicate

R7-3 — "OGÓLNA DOSTĘPNOŚĆ" HAS CREATE SEMANTICS BUT NO TOGGLE/CORRECTION
STATUS: FAIL
CONTRACT:
- owner matrix: an unchecked range is inclusive od-do, returns to the base
  checked state after do, and an existing restriction can have its dates
  corrected or be restored earlier without mutating history
- append_availability is the single append-only owner; availability_id names
  one family and a new version in that family supersedes its predecessor
EVIDENCE:
- brief.md:313-319 specifies only active=True with a fresh availability_id
  for a new UNAVAILABLE_24H block
- that correctly creates an independent block, but no Section 5.1 action
  reuses its availability_id with corrected dates or active=False
- get_current_availability_for_employee returns the current end of every
  family, including inactive ends, but the contract does not define how that
  read drives the promised toggle/restore behavior
IMPACT:
- the control can turn availability off but cannot perform the other half of
  a toggle or the already-frozen correction path; generating a fresh family
  for an edit would leave parallel active restrictions
CLOSURE:
- distinguish creation of a new independent range (fresh availability_id)
  from correction/deactivation of an existing range (same availability_id)
- define how the current record's active flag and inclusive dates are shown
  and how early restoration writes the next append-only version
