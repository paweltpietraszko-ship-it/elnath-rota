OBSZARY GOTOWE — PASS

1. Vertical path i ownership

Kontrakt jednoznacznie wymaga:
Decision Ledger/SQLite -> automatyczna projekcja miesięczna -> PlanningState ->
prevalidation -> solver eligibility -> niezależny validator -> wynik.

PlanningEngine i cały rota/planning/ pozostają bez SQLite, rota.persistence i
Decision Ledger. Persistence nie interpretuje parametrów. Podział ownership
jest zgodny z frozen PlanningEngine no-persistent-state oraz MEMORY-01..03.

2. Projekcja miesięczna

Semantyka jest testowalna i kompletna:
- automatyczne odkrycie wszystkich rodzin site_id;
- daily effective selection przez istniejący algorytm T005;
- inclusive effective_to;
- supersedes/corrects/rejects w środku miesiąca;
- NO_ACTIVE_RULE jako brak slice;
- koalescencja kolejnych dni tej samej wersji;
- exact persisted versions bez modyfikowania effective_to;
- rozdział RESOLVED/NEEDS_RESOLUTION;
- jawny, efemeryczny SiteRuleApplicability w PlanningState.

3. Trzy reguły i parametry

Każdy rule_kind ma zamknięty exact-match identyfikator, exact-shape JSON,
zakres wartości i jednoznaczną semantykę. Zdefiniowano:
- EMPLOYEE_ALLOWED_SHIFT_KINDS;
- EMPLOYEE_ALLOWED_WEEKDAYS;
- EMPLOYEE_FORBIDDEN_SHIFT_KINDS_ON_WEEKDAYS.

Niepuste listy, D/N, ISO weekdays 1..7, błędne typy, brakujące i dodatkowe
klucze są rozstrzygnięte. Day anchor to data rozpoczęcia demandu, także dla N.
Nie pozostaje luka parsera naturalnego języka ani ogólnego DSL.

4. HARD, konflikty i validator

- HARD działa przed objective i przed REPLAN reshuffle;
- reguły łączą się przez AND;
- valid rule-caused infeasibility to DECISION_REQUIRED, nie TECHNICAL_ERROR;
- blocker/violation używa dokładnego rule_version_id;
- validator ma niezależnie od solvera ponownie wykonać wszystkie applicable
  HARD semantics;
- frozen conflict jest autonomiczną granicą z rule_version_id;
- REALIZED nie jest unieważniane retrospektywnie.

5. Integracja i macierz

Macierz A-Q obejmuje baseline, wszystkie trzy reguły, overnight anchor,
supersession/reject, unresolved/informational/soft/error boundaries,
multiple rules, validator, dwa miesiące po restarcie, brak planning I/O,
frozen i REALIZED.

Test N wymaga rzeczywistego SQLite + Decision Ledger + restart + automatyczne
family discovery + monthly projection + real plan() w dwóch miesiącach. Dla
piątku wymaga zarówno negatywnego D, jak i pozytywnego N, więc nie można
uzyskać PASS przez testowanie samego zakazu.

WYMAGA_DECYZJI T7-R1-1 — ZAKRES KATALOGU WZGLĘDEM SITEPROFILE

Ślad kontraktowy:
- frozen SITE-01: Site.profile_id wybiera semantykę SiteProfile;
- architecture reference RULE-08, przywołane przez addendum i brief:
  SiteProfile owns supported profile rule kinds and their interpretation;
- addendum: `INITIAL EXECUTABLE RULE CATALOG — PROFILE OCHRONA`;
- brief: `Profile OCHRONA supports exactly these executable T007 kinds`.

Brakujące rozstrzygnięcie:
- SiteProfile nie zawiera pola profile family/type ani listy supported kinds;
- repo używa wielu legalnych profile_id, m.in. OCHRONA, OCHRONA-FEB,
  TESTPROF i STRESS-*;
- kontrakt nie definiuje, jak rozpoznać, że konkretny SiteProfile jest
  profilem OCHRONA dla potrzeb katalogu.

Co może obecnie zrobić CC — trzy różne zachowania, każde zgodne z częścią
tekstu, lecz dające inne wyniki:
1. wykonywać trzy rule_kind dla każdego SiteProfile;
2. wykonywać je tylko dla literalnego profile_id == "OCHRONA";
3. próbować zgadnąć rodzinę po nazwie/prefiksie, np. OCHRONA-FEB.

To wpływa na FEASIBLE kontra TECHNICAL_ERROR/DECISION_REQUIRED oraz na to, czy
zapamiętana reguła w ogóle ogranicza grafik. Testy minimal_state i benchmark
używają profili innych niż literalne OCHRONA, więc wybór wpłynie też na
budowę macierzy.

Potrzebna jest jedna jawna decyzja właściciela/architekta:
- czy katalog T007 obowiązuje wszystkie aktualnie obsługiwane profile pilota;
- czy tylko profil OCHRONA, a jeśli tak, jaka dokładna, strukturalna cecha
  identyfikuje tę rodzinę (bez inference z tekstu).

Audyt nie wybiera rozwiązania ani nie proponuje nowego pola; wskazuje brak
jednoznacznego oracle wynikający z istniejącego RULE-08.

WYMAGA_DECYZJI T7-R1-2 — UNKNOWN/MALFORMED INFORMATIONAL

Ślad kontraktowy:
- addendum SITE-RULE-EXEC-01 punkt 7: INFORMATIONAL pozostaje
  non-constraining;
- addendum punkt 8: RESOLVED rule claiming executable, ale unsupported lub
  malformed, daje TECHNICAL_ERROR — bez jawnego ograniczenia do HARD;
- brief RULE KIND REGISTRY i Acceptance #7 ograniczają jawny error do
  `Unknown/malformed RESOLVED HARD`;
- brief test I mówi tylko, że RESOLVED INFORMATIONAL ma zero planning
  constraint effect;
- test J mówi `malformed supported parameters` bez wskazania enforcement.

Brakujące rozstrzygnięcie:
Jak traktować applicable RESOLVED INFORMATIONAL, gdy:
- rule_kind jest nieznany; albo
- rule_kind jest wspierany, ale structured_parameters jest malformed?

Dwa możliwe wyniki nie są równoważne:
- pominąć wykonanie jako INFORMATIONAL i kontynuować planowanie;
- zwrócić TECHNICAL_ERROR z rule_version_id jako malformed/unsupported model.

TECHNICAL_ERROR nie jest constraintem, więc zdanie „INFORMATIONAL never
constrains” samo nie rozstrzyga tej różnicy. CC nie powinien wybierać jej
samodzielnie. SOFT jest już rozstrzygnięty osobno i zawsze failuje jawnie w
T007; NEEDS_RESOLUTION także jest jednoznacznie display-only.

Potrzebne jest jedno zdanie w addendum/briefie określające, czy walidacja
unknown/malformed obejmuje RESOLVED INFORMATIONAL, oraz odpowiedni sibling
test w I lub J.
