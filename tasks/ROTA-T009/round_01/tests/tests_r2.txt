Ślad kontraktowy:

   „One application write either succeeds through repository/lifecycle
   operations or leaves the prior durable aggregate intact.”

2. Clarification, OWNER VERSIONING RULE:
   materialna korekta tworzy nowy child i jest „one application action”.

3. Clarification, T009 MANUAL CORRECTION FLOW nakazuje kolejno:
   - create one complete child snapshot;
   - apply correction;
   - make child current;
   - run validator;
   - materialize Deviations.

4. Accepted T008 create_schedule_version() atomowo zapisuje podaną zawartość i
   od razu przełącza current reference. replace_working_snapshot() jest osobną
   transakcją. Nie istnieje bezpieczny stan pośredni, w którym już-current child
   czeka na późniejszą walidację i materializację Deviations.

Scenariusz awarii:

1. application tworzy child bez jeszcze policzonych aktualnych Deviations;
2. T008 zatwierdza transakcję i ustawia child jako current;
3. validator albo późniejszy zapis Deviations kończy się wyjątkiem/awarią;
4. po restarcie widoczny jest nowy current child bez wyniku wymaganej
   rewalidacji i bez prawdziwego zestawu Deviations, zamiast wcześniejszego
   aggregate intact.

CC nie może spełnić jednocześnie literalnej kolejności clarification oraz
globalnej gwarancji atomowości/restartu.

Wymagana korekta jest mała i nie wymaga nowej architektury. Kontrakt powinien
nakazać logicznie:

1. odczytać parent;
2. przygotować pełny child snapshot w pamięci;
3. zastosować korektę w pamięci;
4. zbudować fresh validation context dla przygotowanego child;
5. zwalidować i zmaterializować komplet Deviations w pamięci;
6. jednym atomowym wywołaniem lifecycle zapisać kompletny child wraz z
   Deviations i przełączyć current reference;
7. przy dowolnym błędzie przed/ podczas kroku 6 parent/current pozostaje bez
   zmian.

Nie jest wymagany workflow engine ani nowy event log. Może to być przygotowanie
argumentów przed istniejącym atomowym create_schedule_version(), z najmniejszą
niezbędną adaptacją do effective_from/nowego targetu Deviation.
