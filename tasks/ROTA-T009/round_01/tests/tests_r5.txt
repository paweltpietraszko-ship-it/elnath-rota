-------------------------------------------------------------------------------

Podstawa kontraktowa:

  się w całości, albo pozostawia poprzedni trwały agregat bez zmian;
- R4-1 wymagał fault injection we wszystkich wieloetapowych przepływach.

Trzy rodzeństwa pozostają czerwone:

1. plan_month wykonuje dry-run assemblera, tworzy pierwszą wersję, a następnie
   wykonuje drugi assembler. Awaria drugiego odczytu pozostawia pustą wersję
   i current reference, mimo że PLAN zakończył się wyjątkiem.
2. replan analogicznie tworzy i przełącza child pomiędzy pierwszym i drugim
   assemblerem. Awaria drugiego pozostawia child jako current.
3. training._build_readiness_hook wywołuje save_site_membership(), które
   otwiera własny `with conn:` i commit. Awaria bezpośrednio po tym zapisie
   nie cofa ani membership, ani child/current. W tym samym commicie powstał
   write_site_membership_in_open_transaction(), ale ścieżka treningu go nie
   używa.

Macierz: 3 czerwone przypadki. Poprzedni test szkolenia rzucał przed zapisem,
więc nie sprawdzał najważniejszej granicy „write succeeded, next step failed”.

Wymagana własność naprawy: fault injection po każdym etapie publicznej akcji,
także po pomocniczym zapisie, pozostawia poprzedni current, liczbę wersji i
membership bez zmian. Nie wymagam nowego Unit of Work/frameworka.

R5-2 — HIGH — assembler nie wiąże całego klucza (Site, month, version)
-------------------------------------------------------------------------------

Podstawa kontraktowa:
- brief.md ONE CANONICAL PLANNINGSTATE ASSEMBLER: targetem jest
  `(site_id, month, schedule_version_id)` i exact schedule_version_id;
- nie wolno duplikować target-version Assignments w boundary;
- surrounding/cross-Site context używa current versions, ale target month nie
  jest swoim własnym surrounding context.

Jedna klasa ma trzy warianty:

1. Wersja Site A może zostać jawnie złożona razem z Site/Profile/rosterem B.
2. Wersja sierpnia może zostać jawnie złożona razem z kalendarzem i regułami
   września.
3. Przy jawnej nie-current V1 tego samego Site/miesiąca current V2 wraca jako
   boundary. PlanningState zawiera równocześnie target V1 i drugą migawkę tego
   samego target month z V2, co może fałszować REST/LOAD.

Przyczyną jest sprawdzenie tylko istnienia schedule_version_id oraz filtrowanie
boundary wyłącznie po exact version_id, zamiast spójności całej krotki i
wyłączenia target Site/month.

Macierz: 3 czerwone przypadki.

Wymagana własność naprawy: durable version musi należeć dokładnie do żądanego
Site/month; każdy current target-month snapshot jest wyłączony z boundary,
nie tylko ten o tym samym version_id. Prawdziwe miesiące sąsiednie i inne Site
pozostają w kontekście.

R5-5 — MEDIUM — structured rule seam przyjmuje datetime jako effective_from
-------------------------------------------------------------------------------

Podstawa kontraktowa:
- brief.md operation 7: caller podaje exact effective_from;
- T005 frozen contract: effective_from jest pierwszym dniem obowiązywania i
  typem date; SiteRuleVersion/DecisionRecord muszą mieć tę samą wartość;
- application boundary ma failować przed utrwaleniem wadliwego inputu.

record_structured_rule_decision nie używa istniejącego require_real_date.
Python datetime jest podklasą date, więc write zapisuje pełny timestamp do obu
wierszy. Późniejszy odczyt date.fromisoformat nie rekonstruuje prawidłowego
kontraktowego dnia, lecz DecisionRecord jest już trwale zapisany.

Macierz: 1 czerwony przypadek.

Wymagana własność naprawy: structured rule command odrzuca datetime/None/inny
typ przed record_decision; rzeczywisty date nadal przechodzi.
