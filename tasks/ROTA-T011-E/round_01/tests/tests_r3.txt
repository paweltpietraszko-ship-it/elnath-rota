`from rota.site_memory_types import NewRuleContent`

Niezależny skan AST obu plików potwierdził, że jest to jedyny import `rota.*`
poza dozwoloną powierzchnią. Importów `rota.persistence` rzeczywiście nie ma,
ale brak persistence nie znosi węższego, jawnego wymagania tego tasku.

Właścicielem kontraktu wywołania pozostaje warstwa aplikacji. Moduł

zmiany produkcji ani nowej warstwy.

Warunek zamknięcia: usunąć bezpośredni import `rota.site_memory_types` i
budować wejście do decyzji przez dozwoloną powierzchnię aplikacyjną. Skan AST
obu plików ma następnie wykazać wyłącznie `rota.application.*`, `rota.domain`
oraz zaakceptowany wyjątek `rota.planning.validator`.


FINDING E-R3-2 — CANDIDATEREJECTED NIE JEST PRZYPISANE TESTOWANEJ REGULE HARD

  `select_candidate` z kandydatem łamiącym aktywną regułę HARD;
- test ma dowodzić tej reguły, nie dowolnego innego powodu odrzucenia.

Test 5 tworzy kandydat zawierający tylko jeden Assignment dla jednego demandu,
podczas gdy PlanningState zawiera demand dla każdego dnia miesiąca. Niezależna
diagnostyka `validator.validate` wykazała:

W tej postaci test nadal przejdzie, jeżeli `select_candidate` przestanie
respektować SiteRule: pozostałe braki pokrycia samodzielnie wymuszą
`CandidateRejected`, a końcowe `hard_pass=False` również pozostanie prawdziwe.

To jest klasa błędu „odrzucenie z właściwym statusem, lecz z niezależnego
powodu”. Sam status wyjątku nie dowodzi właściciela decyzji.

Warunek zamknięcia:

- zbudować kompletnego kandydata pokrywającego każdy demand dokładnie raz i
  spełniającego pozostałe HARD;
- potwierdzić, że `validate` odrzuca go przez identyfikator aktywnej wersji
  SiteRule, bez `COVERAGE-01` ani innej niezależnej klasy HARD;
- na tym samym kandydacie asertować `select_candidate -> CandidateRejected`.

Kontrola równoważności może dodatkowo wykazać, że po jawnym `rejects` tej
reguły ten sam kandydat uzyskuje `hard_pass=True`. Nie należy zmieniać silnika
ani `select_candidate`.
